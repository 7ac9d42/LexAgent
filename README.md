# LexAgent

> **一份面向长期人机协作的全局 Agent 基本法。**
> 
> 目标不是让 Agent 无所不能，而是让 Agent 在长期工程协作中始终保持安全、克制、可靠且可预测。

---

> [!NOTE]
> **维护与适用性说明**  
> 本项目是作者在实践中沉淀的全局 Agent 行为规范与安全底线，主要服务于作者本人的日常开发与设备环境，主要目的是为了方便本人。**本项目不承诺定期维护、功能迭代或对外技术支持**。欢迎根据自身工程场景与协作习惯 Fork 或参考定制。

---

## 为什么存在这份配置

随着 AI Agent 深度介入系统研发、运维排障与代码工程，其执行权限与行动边界正在迅速扩张。

在工程实践中，相比“代码写得不够精妙”，更频繁发生且代价惨重的往往是以下高风险事故：

- **窥探凭据**：主动或无意识读取环境变量、私钥与 Token；
- **环境越权**：在远程设备或生产节点私自执行破坏性写操作；
- **系统污染**：擅自提权、修改全局配置或随处安装未经隔离的依赖；
- **代码误伤**：私自向远端推送未经审计的代码、误触 CI/CD 或破坏性回退；
- **范围蔓延**：脱离当次需求目标，借修复之名进行大范围无关重构与格式化；
- **盲目通读**：无节制检索与盲目通读大型文档，导致上下文窗口瞬间塞爆并丢失焦点。

这些问题的根源**并非 Agent 的技术能力不足，而是缺乏明确的工程底线与权限边界约束**。

因此，本配置的核心导向不是让 Agent 变得更“花哨”，而是让 Agent 在长期的生产协作中具备五个关键特质：
**可预测 (Predictable)**、**可审计 (Auditable)**、**可回退 (Reversible)**、**可维护 (Maintainable)** 与 **值得信任 (Trustworthy)**。

## 核心设计目标

```text
                   ┌────────────────────────┐
                   │   1. 防范高风险事故    │  (最高优先级：一次失误即致命)
                   └───────────┬────────────┘
                               ▼
                   ┌────────────────────────┐
                   │   2. 消除重复沟通成本  │  (沉淀全局公理，拒绝每次声明)
                   └───────────┬────────────┘
                               ▼
                   ┌────────────────────────┐
                   │   3. 确保长期可维护性  │  (稳定性优于覆盖率)
                   └────────────────────────┘
```

### 1. 防范高风险事故 (Safety Gate)
优先约束那些**一次失误即可造成灾难性后果、事后极难恢复且爆炸半径极广**的行为：
- 敏感凭据窥探
- 本地破坏性删除与提权
- 远端设备静默写入
- 远端 Git 变更与分支污染

此类风险的控制优先级永远置于“代码风格”与“局部代码优化”之上。

### 2. 消除重复沟通成本 (Engineering Baseline)
将放之四海而皆准的通用工程原则固化为底座公理：
- 最小必要改动 (Minimal Changes)
- 保持简单 (KISS / YAGNI)
- 严禁无关扩张与重构
- 改动必经验证，失败立即回滚
- 严格遵循既有代码风格

这些共识若在每次任务提示词中逐条声明，会造成巨大的重复交互损耗，必须上升为全局刚性约束。

### 3. 确保长期可维护性 (Long-term Stability)
服务于可持续的长期协作，而非单次临时 Prompt 调试：
- **稳定性优于覆盖率**：宁可漏掉边缘场景，也绝不为了迎合个例破坏整体一致性；
- **原则优于清单**：建立清晰的审查门禁与行为模式，而非无休止枚举工具与命令。

## 架构设计哲学：宪法，而非操作手册

本配置不试图覆盖具体的业务场景与工程细节，它在人机协作体系中充当**“宪法”**层级：

```text
                    ┌─────────────────────────┐
                    │    全局宪法 (LexAgent)   │  定义安全边界、权限门禁与工程底线
                    └────────────┬────────────┘
                                 │ (冲突时项目规范优先，但底线不削弱)
                                 ▼
                    ┌─────────────────────────┐
                    │    项目规约 (Project)   │  定义架构、开发规范、测试与分支门禁
                    └────────────┬────────────┘
                                 │ (在规约框架内执行)
                                 ▼
                    ┌─────────────────────────┐
                    │    任务指令 (Task)      │  定义即时目标、当前需求与具体上下文
                    └─────────────────────────┘
```

| 层级 | 载体示例 | 核心职责 |
| :--- | :--- | :--- |
| **全局宪法** | `LexAgent (AGENTS.md)` | 定义全局安全底线、执行防护、隐私隔离与通用工程原则 |
| **项目规约** | 项目根目录 `AGENTS.md` / `CLAUDE.md` / 文档大纲 | 定义项目架构设计、语言规范、工具链约定与提交测试门禁 |
| **任务指令** | 用户的单次交互 Prompt | 描述当前任务目标、上下文信息与交付期望 |

## 三大运行准则

### 1. 规则最小化原则 (Minimal Rules)
> **少而稳，而非多而全。**

```text
规则不断堆叠 ──▶ 上下文被挤占 ──▶ 注意力稀释 ──▶ 关键指令遗忘 ──▶ 执行质量劣化
```

新增任何规则，必须至少满足以下严苛标准之一：
1. **对真实事故具备不可替代的明确防护价值；**
2. **在日常工程实践中长期、高频出现；**
3. **普遍适用于绝大多数工程技术栈与场景；**
4. **无法在项目规约层得到有效约束。**

拒绝因个别孤立案例而不断追加特例规则，配置规模必须严格控制在 Agent 上下文注意力能够长期稳定响应的阈值之内。

### 2. 风险优先原则 (Risk-First Hierarchy)
安全与风险控制永远处于最高优先级，拒绝本末倒置：

```text
凭据隐私隔离 ──▶ 远程设备只读 ──▶ 远端 Git 门禁 ──▶ 破坏性操作防护 ──▶ 工程规范对齐 ──▶ 代码风格优化
(绝对红线)                                                                      (常规诉求)
```

代码格式不规范通常不会导致系统崩溃，但一次未授权的远端写入或敏感 Token 外泄足以引发重大生产灾难。

### 3. 项目优先原则 (Project-First Conflict Resolution)
全局宪法绝不谋求取代项目本地的最佳实践：
- **动工前按需排查**：开展开发前优先检查项目本地规约，但严禁盲目全量通读大型文档库，必须采用目录索引或大纲定向检索以节省上下文；
- **冲突裁决机制**：当项目级专属规约与全局宪法条款发生冲突时，**项目专属规约优先**；
- **底线不可削弱**：未冲突部分——特别是**全局隐私凭证隔离、系统破坏性防护与远端 Git 绝对红线**——持续强制生效，绝不因项目规约而发生降级或豁免。

## 对 Agent 的行为期望

本配置期望 Agent 表现为一名经验丰富、严谨自律的系统工程师，而非无脑执行的自动化脚本：

- **修改前先理解**：修改前先深入理解调用链与上下文，拒绝盲目试错；
- **根据证据分析**：排查问题以日志、调用栈和实际采样为据，拒绝凭空臆测；
- **尊重既有架构**：对齐项目原有代码风格、缩进与命名习惯，绝不随意格式化无关区域；
- **保持最小改动**：专注解决当次核心问题，避免无关扩张，拒绝过度抽象与设计模式堆叠；
- **改动必经闭环验证**：完成修改后必须在本地进行针对性验证；客观条件受限无法验证时如实说明，严禁虚构验证结果；
- **敬畏权限边界**：对长耗时命令主动设限超时，对高危写操作与远端调用保持绝对克制。

## 维护原则

本基本法应保持高度的长期稳定性。

除非出现以下情况：
- 出现全新的高风险破坏场景；
- 暴露重复发生的系统性缺陷；
- 既有条款存在明确的逻辑漏洞与冲突；

否则不应频繁扩充。相比不断追加规则，更重要的是维持规则的清晰性、一致性与绝对可执行性。

## 生效与分发机制

本仓库中的 `AGENTS.md` 可作为全局单一事实源（Single Source of Truth），通过软链接直接分发至各大常用 Coding Agent：

```bash
# 统一指向 LexAgent 的 AGENTS.md
LEX_AGENT_SRC="<Anywhere you like>/AGENTS.md"

# Claude Code
ln -sf "$LEX_AGENT_SRC" ~/.claude/CLAUDE.md

# OpenAI Codex
ln -sf "$LEX_AGENT_SRC" ~/.codex/AGENTS.md

# Google Antigravity / Gemini
ln -sf "$LEX_AGENT_SRC" ~/.gemini/config/rules/AGENTS.md
ln -sf "$LEX_AGENT_SRC" ~/.gemini/config/AGENTS.md
ln -sf "$LEX_AGENT_SRC" ~/.gemini/GEMINI.md

# Pi Coding Agent
ln -sf "$LEX_AGENT_SRC" ~/.pi/agent/AGENTS.md

# DeepSeek DSH
ln -sf "$LEX_AGENT_SRC" ~/.dsh/AGENTS.md

# OpenCode
ln -sf "$LEX_AGENT_SRC" ~/.config/opencode/AGENTS.md
```

后续在此仓库内维护修改 `AGENTS.md`，各 Agent 即可实时同步生效。
